# SpacetimeDB

## When to use

Read this before touching:

- the **Module** (`crates/stdb_module`) — tables, reducers
- the generated **Bindings** (`crates/stdb_bindings`)
- the **Bridge** (`crates/stdb_bevy`)
- the client **connection** code in `crates/game`

See `../CONTEXT.md` for the canonical meaning of Module / Reducer / Bindings / Bridge / Game.

## Critical rules

### 1. Keep all SpacetimeDB versions aligned at 2.4.x

The server (`docker-compose.yml` image tag), the CLI (`.mise/config.toml`), `spacetimedb`
(Module crate), and `spacetimedb-sdk` (client) must share the same major/minor. A mismatch is a
websocket-protocol mismatch. SpacetimeDB 2.4 also requires **rustc ≥ 1.93** — that is why
`rust-toolchain.toml` pins the toolchain. Versions are centralized in the root
`Cargo.toml` `[workspace.dependencies]`.

### 2. Module API (2.4) gotchas

- Tables use **`accessor = <ident>`** (a Rust identifier), not `name = <ident>`. The accessor is
  the method you call: `#[table(accessor = player, public)]` → `ctx.db.player()`. Add `public` so
  clients may subscribe.
- The caller identity is the **method** `ctx.sender()`, not a field.
- Access tables in reducers via `ctx.db.<accessor>()`; unique/primary-key columns give
  `.find()` / `.update()` / `.delete()` (e.g. `ctx.db.player().identity().find(id)`).
- Lifecycle reducers: `#[reducer(init)]`, `#[reducer(client_connected)]`,
  `#[reducer(client_disconnected)]`. A connecting SDK client triggers `client_connected`.

### 3. Never hand-edit `stdb_bindings`

`crates/stdb_bindings/src/module_bindings/` is generated by `just stdb::generate`
(`spacetime generate --lang rust`). It is **committed** so the workspace builds without a running
server, and CI fails if it drifts from the Module. After changing the Module: `just stdb::generate` and
commit the diff. Only `src/lib.rs` (the `pub mod module_bindings;` wrapper) is hand-written.

### 4. The Bridge stays module-agnostic

`stdb_bevy` knows nothing about any Module. It owns the connection behind a builder
(`StdbPlugin::new(DbConnection::builder)…`), hides the native-sync / wasm-async `build()` split, and
pumps the connection once per frame with `frame_tick` — no background thread, so one path drives both
native and wasm. The connection is **`Send + Sync`** (the SDK confines the browser socket to a
`spawn_local` task and keeps the handle behind `Arc<Mutex>` + `Send` callbacks), so it lives in a
normal **`Res<StdbConnection<C>>`** — *not* a `NonSend` resource — and every Game system that calls a
reducer or subscribes is an ordinary multi-threaded system. Lifecycle surfaces as **observer events**
(`StdbConnected` / `StdbDisconnected` / `StdbConnectionError`); table changes as **buffered messages**
(`RowInserted<T>` / `RowUpdated<T>` / `RowDeleted<T>`). The Game opts a table into that message stream
with `stdb_tables! { player => Player }` and subscribes (in the `StdbConnected` observer) via
`StdbConnection`'s `subscription_builder()`. Module-specific code (which tables, which reducers) lives
in `game`. See ADR 0002 for why the connection is `Res` not `NonSend`, and why the Bridge does not
`Box::leak` it.

### 5. Client connection + reads

```rust
use spacetimedb_sdk::{DbContext, Table};        // .db()/.subscription_builder() ; .iter()/.count()
use stdb_bindings::{DbConnection, PlayerTableAccess};   // .player()

DbConnection::builder()
    .with_uri(SPACETIMEDB_URI)              // http/https/ws/wss
    .with_database_name(SPACETIMEDB_MODULE) // the published Module name, e.g. "monster-master"
    .on_connect(|ctx, identity, _token| {
        ctx.subscription_builder()
            .on_applied(|_| info!("subscription applied"))
            .subscribe(["SELECT * FROM player"]);
    })
    .build()?;                              // succeeds before the socket is up; may fail async
```

Read from the local cache after subscribing: `conn.db().player().iter()` / `.count()`. Call
reducers via `conn.reducers().<reducer>(..)`.

### 6. The dev loop

```sh
docker compose up         # SpacetimeDB on :3000 (or `spacetimedb-cli start` without Docker)
just stdb::publish        # build + publish the Module
just stdb::generate       # regenerate Bindings, then commit
just dev::native          # native client
just dev::web             # web client at http://localhost:8080
```

If `publish` fails with `401 Unauthorized: Invalid token: InvalidSignature`, the CLI is sending a
token issued by a previous server instance — the server regenerates its JWT signing keys whenever
its data dir is wiped (e.g. `docker compose down -v` or deleting the data volume). Re-authenticate
with `spacetimedb-cli logout` (or delete `spacetimedb_token` from `~/.config/spacetime/cli.toml`),
then publish again; it performs a fresh server-issued login. The persistent data volume keeps the
keys stable across normal `up`/`down`, so this only bites after a wipe.

### 7. Web (wasm) specifics

- `getrandom` uses its JS backend on wasm — set once in `.cargo/config.toml`
  (`getrandom_backend="wasm_js"`) plus the `wasm_js` feature on the game's wasm-target dep.
- The same `frame_tick`-per-frame Bridge drives both native and wasm — no threads on the web.
- `SPACETIMEDB_URI` / `SPACETIMEDB_MODULE` are baked in at build time (via `.env` + `just`), so the
  deployed web build must be built with the URI of the real server.

### 8. The `wasm-opt` warning on publish is harmless

`spacetime publish` prints "Could not find wasm-opt" and publishes the Module unoptimised. Leave it:
the Module is small (optimization barely matters there — client wasm size is what counts, and trunk
already optimizes that). Installing `binaryen` is not worth it: `spacetime`'s wasm-opt call does not
pass `--enable-bulk-memory`, so it would fail on the bulk-memory ops rustc emits — the same issue we
solve for the client via `data-wasm-opt-params="--all-features"` in `index.html`.

### 9. Inspecting & debugging

There is no psql-style shell or web dashboard for self-hosted SpacetimeDB (the dashboard at
spacetimedb.com is for Cloud databases). Debug via the CLI, wrapped as `just` recipes that target
the local server:

- `just stdb::sql 'SELECT * FROM player'` — read-only SQL. State changes only ever happen through
  reducers; there is no client-side INSERT/UPDATE/DELETE.
- `just stdb::logs -f` — stream the Module's logs (your reducers' `log::info!` / `log::error!`).
- `just stdb::describe` — schema (tables + reducers) as JSON.
- `just stdb::call set_name '"Neo"'` — invoke a reducer by hand (arguments are JSON).
- `spacetimedb-cli subscribe --server <uri> <module> 'SELECT * FROM player'` — live-stream a
  query's rows as they change (useful for watching state during play).

Client (Bevy) log verbosity is controlled by `RUST_LOG` (set in `.env`); the default
`warn,game=trace` shows our `game` logs and silences Bevy's own INFO chatter. Bevy's `LogPlugin`
reads `RUST_LOG` and lets it override its built-in filter.
